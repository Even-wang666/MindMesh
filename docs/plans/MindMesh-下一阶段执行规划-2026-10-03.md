## 4. 需要补进 V1.1 的实施细节

### 4.1 权限必须显式进入 Runtime 请求

当前 `resolveRunAgent()` 只返回工具过滤后的 Agent，`harness.run()` 没有接收 permission。配置工具为空的 Agent 在 chat 与 full 下可以产生相同能力 hash。

V2 必须显式传递主进程验证后的 permission/flavor；不能由 Shell 是否存在或 tools 是否为空推断 full。建议每轮得到一个一致的 Runtime 请求快照：有效 Agent、workspace、flavor、provider revision、DSH/schema version，以及 extended 的插件集合 revision。会话 hash 和实际启动必须使用同一快照，避免等待期间配置变化导致二者不一致。

### 4.2 保留能力快照的现有产品语义

当前已有会话保持 persona 快照，名称/角色实时覆盖，tools/reasoningEffort 跟随当前配置。不要借 Runtime V2 顺手改变这些语义。

`database.getOrCreateRuntimeSession()` 会比较持久化 hash 的 base 与快照 hash；`services.ts` 随后比较实际运行的 effective hash。新增 environment revision 必须同时适配这两处。跨 generation 创建 fresh session，私聊和 Space 按现有历史策略恢复；不能直接复用旧 Home 的 session ID。

### 4.3 隔离需要覆盖重复启动和并发 acquire

`index.ts` 当前没有 `requestSingleInstanceLock()`。两个应用进程使用同一 dataDir 时，同一确定性 key 可能指向同一可写 Home。

V2 建议使用 Electron 单实例锁，第二次启动聚焦已有窗口；如果产品要多实例，必须另行隔离 dataDir/Home。Supervisor 对同一 key 的并发 acquire 还需复用 preparing/starting Promise，防止物化变成异步后重复创建 Host。

不要继续仅以前 12 位 hash 作为 Home 唯一性依据；使用完整 key 或元数据核验。工作目录身份需要明确 Windows 路径规范化规则。

### 4.4 generation 变化不应继续 shutdownAll

目前保存/删除 Provider、删除 Agent/Space、切换 workspace 都会调用 shutdownAll。安装插件后不能复用此路径。

Provider revision 至少覆盖 URL/model/credential revision；credential 使用非明文版本 token，不把密钥 hash 写日志。只让相关旧 Runtime stale，active lease 完成后 retire。取消某一请求、应用退出与 generation 更新要保持独立语义。

删除 Agent/Space 的既有业务效果和运行资源回收，应在 Supervisor 阶段改为按归属处理，并调整当前要求 shutdownAll 的 cleanup 测试；避免不相关会话被关闭。

### 4.5 staging 是兼容验证环境

独立 DSH_HOME 能隔离配置、Session 和 Storage，并不构成第三方 Host 代码的操作系统沙箱。staging 不注入用户真实 Provider 密钥，不复制用户 Skills/persona，不自动运行未批准的 lifecycle scripts，使用临时 workspace 和受控环境。

按目标 DSH 版本验证：无密钥或假凭据是否足以 initialize；stdout 普通文本是否确实让客户端失败；安装命令是否能确保默认阻止构建脚本。使用专门的测试插件检验，不能只根据退出码或 stderr 文案推断安全。

Dynamic validation 复用正式 capability patch 的生成逻辑，包含代表性的 full 配置，并显式关闭 tool-plugin-manager。不同组合和平台可能影响兼容性，兼容缓存应考虑 candidate set、MindMesh patch/schema revision、DSH version 和相关平台条件。缓存不能替代每次 mutation 的完整候选集合 staging。

### 4.6 desired state 提交需要覆盖中断与重新物化

安装、更新、删除、启用和停用都先构造候选集合，在一个 mutation 串行队列中验证后事务提交。验证失败或取消时 DB 原状态保留。

正式物化完成前不标 ready；检查 Home 元数据和 profile composition。应用在下载、验证、提交或物化中退出后，重启以 DB desired state 为准恢复/重建，未完成 staging 不变成正式状态。

插件 exact direct version 并不自动保证整个传递依赖图一致。插件阶段需要验证 staging 与正式物化的解析结果是否一致，并确定是否保留已验证的 lockfile/依赖解析凭据。只复用不可变 composition 资料，不复制 live Home 的 sessions/storages。

### 4.7 Agent 安装需要解决重名与模型默认值

当前 `agents.name` 唯一；来源去重与展示名重名是不同问题。使用 `(source, sourceId)` 去重，安装新来源时生成确定的可用名称，不能覆盖用户手建同名 Agent。

当前没有统一、持久化的全局默认模型，向导初始值是 DeepSeek。V1 建议安装时沿用向导当前默认；未配置时可演示，用户随后编辑。不要为了 Agent 安装额外引入一整套默认模型设置。

模板安装 tools=[]，保留来源 revision、内容和许可信息；不从 persona 文字推导工具授权，也不自动更新用户编辑过的 persona。

### 4.8 Team 安装不能直接套现有 createSpace

`createSpace()` 自己开启 BEGIN/COMMIT。直接在外层 Team 事务中调用它会产生事务嵌套问题。

先在事务外完成远程内容获取、normalize、引用解析，再通过一个 DB 业务操作原子完成复用/创建 Agent、创建 Space 和成员。事务内只做本地数据库操作，失败回滚且不删除已有 Agent。

要让 Installed/Open 在重启后工作，需要持久化 Team 来源到 Space 的映射。建议给 Space 增加最小来源 metadata 或一个轻量关联记录，不创建独立 Team 生命周期表。

### 4.9 迁移和清理先保护回滚

现有 schema 是 CREATE IF NOT EXISTS 与按列探测的手工迁移，没有明确 DB schema version。新增插件表时引入集中、版本化、事务性的迁移，并验证旧库和重复启动。

目前 Home cleanup 按 session 引用立即清理未引用目录，没有文档提出的 7 天保留机制。V2 使用新 namespace、元数据和 retention；保护 preparing、starting、busy、active Home，保留 legacy homes 供回滚。进程空闲淘汰 TTL 与磁盘 Home 保留 TTL 分开。

## 7. 范围控制与回滚

- 暂不做动态 Tool discovery、per-Agent plugin ACL、插件 UI 嵌入、workflow/DAG、长期 memory/knowledge、支付或多用户。
- 不引入第二套 Cordis Host、不 fork DSH、不共享可写 Home、不执行 Catalog command 字符串。
- 沿用已有 Skill/hash/错误日志实现，按真实职责拆文件；不先创建文档推荐的全部空目录或薄封装。
- DSH 升级失败回滚依赖和兼容调整；不删除用户 dataDir。
- V2 迁移保留旧 homes 和历史；schema 升级需有旧库备份/回滚说明，不能只靠切换代码版本。
- staging 失败保留 bounded diagnostics 后 TTL 清理；DB desired state 不动。
- extended 失败提供可解释诊断，core chat/workspace 仍可用；修复/disable/remove 都重新验证候选集合。
- 用户已有安装器、package.json、法律文档等未提交变更保持独立，实施时不覆盖、不混进功能提交。
